# User management API (`OrchardCore.Users`)

The User management API lists and retrieves tenant users without exposing credentials, and creates, updates, disables, or deletes accounts through Orchard Core Identity services.

Enable the owning feature, `OrchardCore.Users` (**Users**), and configure `OrchardCore.RemoteManagement`. Role assignment requires the `OrchardCore.Roles` feature; without an `IRoleService`, requested roles resolve to an empty set. See [Remote Management authentication](../authentication/README.md).

## Authentication and authorization

Every operation first requires:

- an access token accepted by the `Api` authentication scheme, sent as `Authorization: Bearer <token>`;
- an authenticated principal with **Access remote management API** (`AccessRemoteManagement`).

Operations then enforce resource-aware user permissions:

| Operation | Permission |
| --- | --- |
| List | **List all users** (`ListUsers`), or a role-scoped `ListUsersInRole_<role>` grant accepted by the user authorization handler |
| Get | **View user profiles** (`View Users`) |
| Create | **Edit any user** (`EditUsers`), including an applicable role-scoped edit grant |
| Update, disable | **Edit any user** (`EditUsers`), an applicable `EditUsersInRole_<role>` grant, or **Edit own user information** (`ManageOwnUserInformation`) when editing the authenticated user's account |
| Delete | **Delete any user** (`DeleteUsers`) or an applicable `DeleteUsersInRole_<role>` grant |

For every requested role on create or update, the caller also needs **Assign any role to users** (`AssignRoleToUsers`) or `AssignRoleToUsers_<role>` for that specific assignable role. Delete/assign dynamic grants are not generated for the administrator role.

`ManageUsers` implies the general view/edit/delete permissions; `EditUsers` and `DeleteUsers` imply `ListUsers`. Exact role-scoped permission names are dynamic because the role name is appended verbatim to the permission template.

Antiforgery validation is disabled. An absent or invalid token produces `401 Unauthorized`; an authenticated principal missing a required permission produces `403 Forbidden`.

## Base route

All paths are relative to the tenant URL:

```text
/api/users
```

## Endpoints

| Method | Path | OpenAPI operation ID | Description | Permission |
| --- | --- | --- | --- | --- |
| `GET` | `/api/users` | `ApiListUsers` | List and filter visible users. | `ListUsers` or role-scoped equivalent |
| `GET` | `/api/users/{userId}` | `ApiGetUser` | Get one visible user. | `View Users` |
| `POST` | `/api/users` | `ApiCreateUser` | Create a user and assign authorized roles. | `EditUsers`, plus role-assignment permissions |
| `PUT` | `/api/users/{userId}` | `ApiUpdateUser` | Update an account and authorized roles. | Resource-aware `EditUsers`, plus role-assignment permissions |
| `POST` | `/api/users/{userId}:disable` | `ApiDisableUser` | Disable an account. | Resource-aware `EditUsers` |
| `DELETE` | `/api/users/{userId}` | `ApiDeleteUser` | Delete an account. | Resource-aware `DeleteUsers` |

## User representation

| Property | Type | Description |
| --- | --- | --- |
| `userId` | string | Stable user ID generated by the configured user store. |
| `userName` | string or `null` | Sign-in/user name. |
| `email` | string or `null` | Email address. |
| `phoneNumber` | string or `null` | Phone number. |
| `emailConfirmed` | boolean | Whether the email is confirmed. |
| `isEnabled` | boolean | Whether the Orchard Core account is enabled. |
| `isLockoutEnabled` | boolean | Whether Identity lockout can apply to the account. |
| `lockoutEndUtc` | RFC 3339 string or `null` | Lockout end instant, or `null` when there is no timed lockout. |
| `accessFailedCount` | integer | Current failed-access count. |
| `roleNames` | array of strings | Current roles, sorted case-insensitively. |

Password hashes, security stamps, reset tokens, login providers, claims, and other secrets are never included.

## Paging envelope

The list operation returns:

| Property | Type | Description |
| --- | --- | --- |
| `skip` | integer | Applied zero-based offset. |
| `take` | integer | Requested page size. |
| `totalCount` | integer | Filtered count before paging. |
| `items` | array of user objects | Current page, containing at most `take` entries. |

## List users

```http
GET /api/users
```

The endpoint reuses the extensible Users admin-list filter and query services. The built-in provider applies the filters below; enabled features can contribute additional query behavior.

### Query parameters

| Name | Type | Required | Default | Constraints and behavior |
| --- | --- | --- | --- | --- |
| `skip` | integer | No | `0` | Zero or greater. |
| `take` | integer | No | `50` | From `1` through `200`. |
| `search` | string | No | — | Built-in provider: case-insensitive normalized substring search of user name. Spaces and quotes are escaped before parsing. |
| `email` | string | No | — | Built-in provider: case-insensitive normalized substring search of email. |
| `role` | string | No | — | Built-in provider: normalized exact role-name match. |
| `enabled` | boolean | No | — | `true` filters to enabled users; `false` filters to disabled users. |
| `sort` | string | No | `Name` | `Name` or `Email`, parsed case-insensitively. An unrecognized value falls back to normalized user-name ordering. |

### Request

```http
GET /api/users?role=Editor&enabled=true&sort=Email&skip=0&take=50
Authorization: Bearer eyJ...
Accept: application/json
```

### `200 OK`

```json
{
  "skip": 0,
  "take": 50,
  "totalCount": 1,
  "items": [
    {
      "userId": "4g3v21zq5xk9a7n2",
      "userName": "alice",
      "email": "alice@example.com",
      "phoneNumber": "+1-555-0100",
      "emailConfirmed": true,
      "isEnabled": true,
      "isLockoutEnabled": false,
      "lockoutEndUtc": null,
      "accessFailedCount": 0,
      "roleNames": [
        "Author",
        "Editor"
      ]
    }
  ]
}
```

User IDs and account values are dynamic. `totalCount` is the filtered count before paging; `items` contains at most `take` entries.

### Responses

| Status | Meaning |
| --- | --- |
| `200 OK` | The paged user list. |
| `400 Bad Request` | Invalid `skip` or `take`. |
| `401 Unauthorized` | The bearer token is absent or rejected. |
| `403 Forbidden` | A required permission is missing. |

## Create a user

```http
POST /api/users
```

### Headers and JSON body

`Content-Type: application/json` and a JSON body are required.

| Property | Type | Required | Default | Constraints and behavior |
| --- | --- | --- | --- | --- |
| `userName` | string | Yes | `""` | Validated by the configured Identity user validators. The default allowed characters are `abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789-._+`, but tenant settings can replace this set. The normalized name must be unique. |
| `email` | string or `null` | Conditional | `null` | Validated by Identity. It must be present, valid, and unique when the tenant's `RequireUniqueEmail` setting is enabled (the Orchard Core default); otherwise requirements come from configured validators. |
| `phoneNumber` | string or `null` | No | `null` | Stored as supplied, subject to configured Identity behavior. |
| `password` | string or `null` | No | `null` | Accounts may be created without a password. A nonblank password must satisfy the tenant's configured Identity password policy. |
| `emailConfirmed` | boolean | No | `false` | Initial email-confirmation state. |
| `isEnabled` | boolean | No | `true` | Initial Orchard Core account state. |
| `roleNames` | array of strings | No | `[]` | Blank and case-insensitive duplicate entries are ignored. Every remaining name must identify an assignable role and pass the role-specific assignment permission check. |

Password length, unique-character, digit, lower/upper-case, and non-alphanumeric constraints are dynamic `IdentityOptions` values. Validation messages report the active requirements.

### Request

```http
POST /api/users
Authorization: Bearer eyJ...
Content-Type: application/json
Accept: application/json

{
  "userName": "alice",
  "email": "alice@example.com",
  "phoneNumber": "+1-555-0100",
  "password": "Example-password-1",
  "emailConfirmed": true,
  "isEnabled": true,
  "roleNames": [
    "Editor"
  ]
}
```

### `201 Created`

The `Location` header contains the generated, URL-escaped user ID.

```http
HTTP/1.1 201 Created
Location: /api/users/4g3v21zq5xk9a7n2
Content-Type: application/json
```

```json
{
  "userId": "4g3v21zq5xk9a7n2",
  "userName": "alice",
  "email": "alice@example.com",
  "phoneNumber": "+1-555-0100",
  "emailConfirmed": true,
  "isEnabled": true,
  "isLockoutEnabled": false,
  "lockoutEndUtc": null,
  "accessFailedCount": 0,
  "roleNames": [
    "Editor"
  ]
}
```

### Responses

| Status | Meaning |
| --- | --- |
| `201 Created` | The user was created. |
| `400 Bad Request` | Missing/malformed JSON; Identity validation failure; invalid/unauthorized role assignment. |
| `401 Unauthorized` | The bearer token is absent or rejected. |
| `403 Forbidden` | The caller cannot create this user. Role-assignment authorization failures are instead returned as `400` validation errors. |

## Update a user

```http
PUT /api/users/{userId}
```

### Parameters and JSON body

| Location | Name | Type | Required | Default | Constraints and behavior |
| --- | --- | --- | --- | --- | --- |
| Path | `userId` | string | Yes | — | Existing user ID. |
| Header | `Content-Type` | string | Yes | — | `application/json`. |
| Body | `userName` | string or `null` | No | `null` | Non-null replaces the user name and is Identity-validated. Omission/`null` leaves it unchanged. |
| Body | `email` | string or `null` | No | `null` | Non-null replaces the email and is Identity-validated. An empty string can clear it when validators permit; omission/`null` leaves it unchanged. |
| Body | `phoneNumber` | string or `null` | No | `null` | Non-null replaces the phone number; an empty string clears it. Omission/`null` leaves it unchanged. |
| Body | `password` | string or `null` | No | `null` | A nonblank value resets the password using a generated reset token and the active password policy. Omission, `null`, empty, or whitespace leaves it unchanged. |
| Body | `emailConfirmed` | boolean or `null` | No | `null` | Non-null replaces the confirmation state. |
| Body | `isEnabled` | boolean or `null` | No | `null` | Non-null enables/disables through `IUserService`; omission/`null` leaves state unchanged. |
| Body | `roleNames` | array of strings or `null` | No | `null` | A non-null array replaces role membership after assignability/permission validation. Omission/`null` leaves roles unchanged. `[]` requests removal of all roles, subject to the sole-enabled-administrator safeguard. |

The JSON body itself is required.

When roles change, removals occur before additions. The sole enabled user in the configured `Administrator` role retains that role even if it is absent from `roleNames`. Removing at least one role updates the security stamp.

The endpoint updates the account fields before resetting the password or changing enabled state. It does not provide transactional rollback across those stages; a later validation failure can therefore follow an earlier persisted account update.

### Request

```http
PUT /api/users/4g3v21zq5xk9a7n2
Authorization: Bearer eyJ...
Content-Type: application/json
Accept: application/json

{
  "email": "alice.new@example.com",
  "isEnabled": true,
  "roleNames": [
    "Author",
    "Editor"
  ]
}
```

### `200 OK`

```json
{
  "userId": "4g3v21zq5xk9a7n2",
  "userName": "alice",
  "email": "alice.new@example.com",
  "phoneNumber": "+1-555-0100",
  "emailConfirmed": true,
  "isEnabled": true,
  "isLockoutEnabled": false,
  "lockoutEndUtc": null,
  "accessFailedCount": 0,
  "roleNames": [
    "Author",
    "Editor"
  ]
}
```

### Responses

| Status | Meaning |
| --- | --- |
| `200 OK` | The user was updated. |
| `400 Bad Request` | Missing/malformed JSON; Identity, password, role, or enable/disable validation failure. |
| `401 Unauthorized` | The bearer token is absent or rejected. |
| `403 Forbidden` | The caller cannot edit this user. Role-assignment authorization failures are instead returned as `400` validation errors. |
| `404 Not Found` | The user manager cannot resolve `userId`. |


### Path parameters

| Name | Type | Required | Constraints |

## Error and validation responses

Application-level errors use `application/problem+json`. English messages shown here are localizable except for endpoint-supplied invariant role/enable messages.

Role assignment failures use the exact `RoleNames` model key:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "A validation error occurred.",
  "status": 400,
  "errors": {
    "RoleNames": [
      "Role 'MissingRole' cannot be assigned.",
      "You do not have permission to assign role 'Editor'."
    ]
  }
}
```

Identity validation uses keys such as `UserName`, `Email`, and `Password`; active tenant settings determine which errors appear:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "A validation error occurred.",
  "status": 400,
  "errors": {
    "UserName": [
      "User name 'alice' is already used."
    ],
    "Password": [
      "Passwords must have at least one digit character ('0'-'9')."
    ]
  }
}
```

An enable/disable service failure uses the empty key:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "A validation error occurred.",
  "status": 400,
  "errors": {
    "": [
      "Could not disable the user."
    ]
  }
}
```

The dedicated disable operation instead returns:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Bad request",
  "status": 400,
  "detail": "Could not disable the user."
}
```

Unknown user:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Not Found",
  "status": 404,
  "detail": "User not found."
}
```

The update endpoint constructs its not-found response directly and uses different title casing:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.5",
  "title": "Not found",
  "status": 404,
  "detail": "User not found."
}
```

If the Identity user manager rejects deletion, `detail` contains its error descriptions joined with `, `:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Could not delete the user.",
  "status": 400,
  "detail": "Identity user manager error."
}
```

Operation-specific permission failure:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.4",
  "title": "Forbidden",
  "status": 403,
  "detail": "You do not have sufficient permissions to complete this request"
}
```

Invalid paging uses `Bad request` with either `Skip must be zero or greater and take must be greater than zero.` or `Take cannot exceed 200.` Authentication-policy responses are produced by the configured `Api` authentication handler; their body is handler-dependent.

These endpoints do not emit `409 Conflict`. Duplicate names/emails and other Identity conflicts are returned as `400 Bad Request` validation problems.
